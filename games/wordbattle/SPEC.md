## 0. 한 줄 요약

**턴제 영어 끝말잇기 검술 대결.** 앞 단어의 마지막 글자로 시작하는 단어를 제한시간 안에
입력하면 상대 HP를 깎는다. **v1은 AI 기사와의 싱글 대전**, v1.1에서 온라인 2인 대전을 붙인다.

## 1. 종목 확정 — BRIEF 3안 중 2안

`BRIEF.md`는 3안(단어 만들기 / 영어 끝말잇기 / 뜻 맞히기 속도전) 중 담당이 고르라고 했으나,
**사용자가 담당 배정 시 "영어 끝말잇기"로 직접 지정**했다. 이 선택은 재검토 대상이 아니다.

컨셉 정합성: 사이트명 **Englknight = English + knight**. 끝말잇기는
"내가 아는 단어의 총량"이 곧 전투력이 되는 구조라, *영어를 무기로 쓰는 기사* 컨셉과
직접 맞물린다. 테트리스의 부활 퀴즈처럼 곁가지로 붙은 영어가 아니라 **영어가 게임 메커닉 자체**다.

## 2. 핵심 리스크 — 단어 판정 (조사 결과)

BRIEF와 게임 관리자가 최대 리스크로 지목한 항목이다. **실측으로 조사했고, 결론이 바뀌었다.**

### 2.1 1순위 후보였던 `/usr/share/dict/words`(web2)는 쓸 수 없다

macOS 기본 탑재 사전이고 저작권도 깨끗하다(`/usr/share/dict/README`: *"The 1934 copyright has
lapsed"* — Webster's Second International 1934년판, 퍼블릭 도메인). 235,976 항목,
3~15자 순수 알파벳만 추리면 **204,096개**. 규모만 보면 충분해 보였다.

**그런데 실제로 단어를 넣어보니 두 가지 치명적 결함이 나왔다.**

**결함 ① 굴절형(복수형·과거형·진행형)이 대부분 없다.** 직접 조회한 결과:

| 입력 | web2 | 입력 | web2 |
|---|---|---|---|
| `books` | **없음** | `played` | **없음** |
| `words` | **없음** | `playing` | **없음** |
| `games` | **없음** | `walked` | **없음** |
| `friends` | **없음** | `boxes` | **없음** |
| `cats` | **없음** | `houses` | **없음** |
| `dogs` | 있음 | `running` | 있음 |

web2는 표제어(lemma) 사전이라 굴절형 수록이 들쭉날쭉하다. `dogs`는 되는데 `cats`는 안 되고,
`running`은 되는데 `playing`은 안 된다. **플레이어가 `books`를 넣었다 거부당하는 순간 게임은 끝난다.**
게임 관리자가 말한 *"이게 왜 안 돼?"* 가 첫 3턴 안에 반드시 나온다.

**결함 ② 1934년 사전이라 현대어가 없다.** 흔한 현대 단어 43개를 조회해 10개가 누락:
`email` `internet` `online` `website` `blog` `laptop` `smartphone` `download` `teenager` `okay`.
(`computer` `robot` `television` `pizza` `jeans` 등은 있다.)

→ **web2 단독 사용 불가.** 굴절형을 규칙으로 생성(`-s`/`-ed`/`-ing`)하는 우회도 검토했으나,
비단어를 대량 생산하고(`informations`, `knowed`) 불규칙형을 못 잡아 **채택하지 않는다.**

### 2.2.1 ⚠ 남은 구멍: 현대어 (새로 발견)

**web2의 결함 ②(현대어)는 ENABLE에서도 해결되지 않았다.** ENABLE은 1997년경 리스트다.
현대 어휘 60개 표본을 조회해 **33개(55%)가 누락**:

> `email` `internet` `online` `website` `blog` `app` `apps` `wifi` `emoji` `podcast`
> `username` `login` `hashtag` `meme` `smartphone` `selfie` `blogger` `texting`
> `malware` `firewall` `webcam` `bluetooth` `spam` `cyber` `ecommerce` `smartwatch` …

`laptop` `download` `teenager` `okay` `database` `pixel` `router` 등은 있다.

**이건 학습자가 가장 먼저 떠올리는 단어들이다.** `email`, `internet`, `app`이 거부되면
사전 규모가 17만이어도 신뢰가 무너진다.

→ **보강 목록 `extra.js` 작성 완료 — 350개.**

후보를 추측으로 고르지 않고 **568개 후보를 전부 ENABLE에 대조해 실제로 빠진 것만** 담았다.
굴절형도 함께 넣었다(`app`/`apps`, `blog`/`blogs`/`blogged`/`blogging`/`blogger`).

**제외한 것과 이유** — 걸러낸 기준을 남긴다:
| 제외 | 예 | 이유 |
|---|---|---|
| 고유명사·상표 | `chatgpt` `bitcoin` `roomba` `faceid` `touchid` | ENABLE의 고유명사 배제 원칙과 일관 |
| 문자로 읽는 약어 | `url` `usb` | §3.5 약어 배제 |
| 두 낱말이 옳은 것 | `qrcode` `solarpanel` `carsharing` `windfarm` | 한 낱말이 아니다 |
| 원형이 없는 억지 파생 | `googling`(원형 `google` 미수록) | 일관성 |
| 16자 이상 | `cryptocurrencies` `videoconferencing` | 길이 제한 |

**관리자 권고는 400개였으나 350개다.** 정당하게 넣을 수 있는 현대 어휘를 다 담은 결과이고,
**숫자를 맞추려고 없는 말을 지어내지 않았다.** 부족하면 실플레이의 거부 목록(§2.4)으로 늘린다.

**부수 확인 — 기초 생활 어휘에는 구멍이 없다.** 걱정돼 `strawberry` `sandwich` `grandmother`
`basketball` `motorcycle` `pharmacy` 등 일상어 200여 개를 대조했는데 **ENABLE이 전부 덮고 있었다.**
빠진 것은 `whiteboard` `seatbelt` `voicemail` `cellphone` 같은 현대 조어뿐이었다.

**⚠ `extra.js`는 판정에만 쓰고 AI 단어 풀에서는 제외한다.**
표준 사전에 없는 조어가 섞여 있어 **AI가 내면 플레이어가 납득하지 못한다.**
보강 목록은 **플레이어를 돕기만 하고 불리하게는 작용하지 않도록** 비대칭을 유지한다.
이 비대칭 덕분에 보강 목록을 넉넉히 넣는 쪽이 안전하다 — 과다 수용의 위험이 거의 없다.

### 2.3 사전 내장 방식 — **굽기 완료 ✅ (실측 반영)**

```
dict.js   — ENABLE 3~15자 168,452개, 접두사 압축(front-coding). 검증 전용
extra.js  — 현대 어휘 보강 350개 (§2.2.1). 판정 전용, AI 풀 제외
core.js   — 기초 영단어 1,000개 + 한글 뜻 + 차단 목록. 손으로 큐레이션·전량 재검증
```

세 파일의 단어를 **하나의 `Set`으로 합쳐** 판정한다. 판정 시점에는 출처를 구분하지 않는다.

**압축 실측 — 예상보다 크게 좋았다:**

| 항목 | 스펙 초안 예상 | **실측** |
|---|---|---|
| 원본(개행 포함) | 1.74 MB | 1,665,769 B |
| 압축 후 | 0.8~0.9 MB | **543,251 B (32.6%)** |
| `dict.js` 파일 | — | **544,587 B ≈ 532 KB** |

**로딩 실측 (브라우저, 로컬 서버):**

| 단계 | 시간 |
|---|---|
| script 평가 | 7.0 ms |
| `unpack()` → 168,452개 배열 | 11.6 ms |
| `Set` 구축 | 13.4 ms |
| **합계** | **32.0 ms** |

초안에서 "100~200ms, 로딩 화면에서 흡수"라고 썼으나 **32ms**였다.
§12에 미비점으로 올려둔 "모바일 첫 로딩 부담"은 **해소**로 본다(모바일이 5배 느려도 160ms).
로딩 화면은 그대로 두되 체감되지 않을 것이다.

**무결성 검증:** 구운 `dict.js`의 `PACKED`를 다시 풀어 원본과 대조 —
**168,452개 전량 왕복 무손실**, 정렬·무중복 유지, 형식 위반 0.

**압축 방식:** 정렬된 목록에서 앞 단어와 공유하는 접두사 길이를 마커 1글자(`chr(48+n)`)로 적고
접미사만 잇는다. **마커는 비소문자, 접미사는 소문자라 구분자가 필요 없다** — 그리디 파싱으로 푼다.
굽는 스크립트는 `_source/build_dict.py`.

### 2.4 미수록 단어 처리 방침 — 게임 관리자 질의 답변

> 질의: *"없는 단어를 어떻게 처리할지(거부/경고/통과)"*

**거부한다. 단, 세 가지를 함께 넣는다.**

1. **문구로 책임을 사전에 둔다.** `"틀렸습니다"`(플레이어 탓) ✗ →
   **`"내장 사전에 없는 단어입니다"`**(사전 탓) ○. 같은 거부라도 체감이 다르다.
2. **턴 시간이 남아 있으면 재입력을 허용한다.** 한 번 거부가 곧 실패가 아니다.
   실패는 **시간 초과일 때만** 확정된다. 이게 이 방침의 핵심 완충 장치다.
3. **게임 종료 후 "거부된 단어" 목록을 보여주고 복사 버튼을 단다.**
   서버가 없어 자동 제보는 불가능하니, 사용자가 담당에게 넘겨 사전을 보강하는 경로를 만든다.

"통과"를 택하지 않은 이유: 아무 문자열이나 통과하면 `asdf`로 이길 수 있어 게임이 성립하지 않는다.

## 3. 판정 규칙 (확정)

입력을 소문자화하고 앞뒤 공백을 제거한 뒤, 아래를 **순서대로** 검사한다.

| # | 규칙 | 실패 시 문구 |
|---|---|---|
| ① | 알파벳 `a~z`만. 공백·하이픈·숫자·기호 불가 | `영어 알파벳만 입력하세요` |
| ② | **3글자 이상** 15글자 이하 | `3글자 이상이어야 합니다` |
| ③ | 이어야 할 첫 글자와 일치 | `'{X}'(으)로 시작해야 합니다` |
| ④ | 이번 판에 안 나온 단어 | `이미 나온 단어입니다` |
| ⑤ | `dict.js`에 수록 | `내장 사전에 없는 단어입니다` |
| ⑥ | 차단 목록에 없음 | `이 단어는 사용할 수 없습니다` |

### 3.1 왜 2글자를 막는가
ENABLE의 2글자 단어는 `aa`(용암), `xu`(베트남 화폐), `qi` 등 **스크래블 전용어가 대부분**이라
"이게 단어라고?"라는 반대 방향의 불신을 부른다. 또 2글자만 반복하면 전투가 늘어진다.
3글자 하한은 그 둘을 동시에 막는다.

### 3.2 대소문자·표기
전부 소문자로 정규화해 비교하고, 화면에는 입력한 그대로가 아니라 **소문자로 통일해** 표시한다.

### 3.3 재사용 금지 범위
**한 판 안에서만** 금지한다. 판이 끝나면 초기화. AI가 낸 단어도 같은 목록에 들어간다.

### 3.4 이어붙일 글자
직전 단어의 **마지막 글자 1개**. (한국식 두음법칙 같은 예외 없음)

### 3.5 고유명사·약어
ENABLE에 애초에 없어 규칙 ⑤가 자동으로 걸러낸다. 별도 처리 불필요.

### 3.6 차단 목록
172k 리스트에는 욕설·비속어·차별어가 포함되어 있다. 사이트가 공개 배포되고
어린 사용자도 있을 수 있으므로 **차단 목록(수십 개)을 별도 배열로 관리**해 규칙 ⑥에서 막는다.
AI 풀에서도 제외한다.

## 4. 막다른 글자 문제 (ENABLE 실측 → 구제 규칙)

끝말잇기 설계에서 가장 자주 게임을 망치는 지점이다. **실제 배포할 ENABLE 168,452개로
글자별 시작/끝 단어 수를 전수 집계**했다. (초안의 web2 기준 수치는 폐기했다.)

| 글자 | 시작 | 끝 | 착지/산출 배율 | 판정 |
|---|---:|---:|---:|---|
| **y** | **544** | **12,763** | **23.5** | 🔴 **구제 대상** |
| **x** | **133** | 357 | **2.7** | 🔴 **구제 대상** |
| s | 18,677 | 62,883 | 3.4 | 안전 — 착지가 잦지만 산출이 압도적 |
| e | 6,840 | 16,767 | 2.5 | 안전 |
| g | 5,537 | 12,947 | 2.3 | 안전 |
| n | 4,206 | 7,376 | 1.8 | 안전 |
| d | 9,858 | 15,772 | 1.6 | 안전 |
| z | 531 | 80 | 0.15 | 안전 — 애초에 착지할 일이 드물다 |
| j | 1,370 | 7 | 0.005 | 안전 |
| q | 805 | 3 | 0.004 | 안전 |
| v | 2,710 | 17 | 0.006 | 안전 |

**핵심 발견 1 — `s`는 위협이 아니다.** ENABLE은 복수형을 전부 포함해 **전체의 37%가 s로 끝난다.**
착지가 매우 잦지만 s로 시작하는 단어가 18,677개라 마르지 않는다. 오히려 게임을 굴러가게 하는 윤활유다.

**핵심 발견 2 — 진짜 위험한 건 `y`와 `x` 둘뿐이다.**
- **y**: `-ly` `-ty` `-ry` 때문에 12,763개가 y로 끝나는데 y로 시작하는 건 544개. **23.5배.**
- **x**: x로 시작하는 133개를 **전량 출력해 확인**한 결과 `xanthan` `xebec` `xenogamy` `xerarch`
  `xylocarp` `xyst`처럼 **거의 전부 전문어·사어**다. 학습자가 아는 건 `xylophone` `xenon` `xerox`
  **사실상 3개**. 반면 `box` `fix` `six` `tax` `mix`로 착지는 자주 한다.

### 4.1 ⚠ 초안에서 바뀐 결정: `y`도 구제 대상에 넣는다

> 초안에서는 *"y는 544개면 한 판을 버티기에 충분하니 구제 대상에서 뺀다"* 고 썼다. **철회한다.**

y로 시작하는 544개를 실제로 뽑아 보니 `yaff` `yaird` `yald` `yamen` `yapok` `yaud` `yauld`
`yech` `yegg` `yeld` `yelk` `yerba` `yerk` `yett` `yeuk` `yill` `yince` `yird` `yirr` `ylem` 처럼
**대부분 스크래블 전용 희귀어**였다. 학습자가 실제로 낼 수 있는 건 `yes` `yellow` `young` `year`
`your` `yard` `youth` `yoga` `yogurt` `yawn` `yell` `yield` `yesterday` `yet` 수준으로 **20개 안팎**이다.
**착지는 12,763번인데 낼 수 있는 건 20개** — 재사용 금지와 겹치면 서너 번 만에 고갈된다.
사전의 절대 개수가 아니라 **학습자 기준 가용 개수**로 판단해야 했다.

### 4.2 구제 글자 선정 기준 (데이터로 자동 선정)

하드코딩하지 않고, `dict.js`를 구울 때 아래 식으로 뽑아 상수로 박는다.

```
구제 글자  ⟺  (끝나는 단어 수 ÷ 시작하는 단어 수) ≥ 2.0
             AND  시작하는 단어 수 < 1,000
```

- 1번 조건만 쓰면 `s`(3.4) `e`(2.5) `g`(2.3)까지 걸려 게임이 헐거워진다 → **산출량 하한**을 함께 건다.
- 2번 조건만 쓰면 `z`(531) `q`(805)가 걸리는데, 둘은 **착지 자체가 드물어** 구제할 필요가 없다.
- 두 조건을 함께 적용하면 ENABLE 168,452개에서 **정확히 `{x, y}` 두 글자만 선정**된다.
- 게임 관리자도 독립 집계 후 *"배율만 쓰면 `e`가 걸린다. 절대량을 주 기준으로, 배율은 보조로"* 를
  지적했다. **같은 결론에 도달했다** — 위 식이 정확히 그 구조다(절대량 하한 + 배율 보조).

### 4.3 구제 규칙 (확정)

**막다른 글자(`x`, `y`)로 끝나는 단어가 나오면, 다음 차례는 그 글자 대신
<u>끝에서 두 번째 글자</u>로 시작해도 된다.** (둘 중 하나를 고르는 선택지이지, 강제가 아니다)

> `box` → `x` 또는 `o` · `happy` → `y` 또는 `p`

- 강제가 아니라 **선택**이므로, 아는 사람은 `xylophone`·`yellow`를 그대로 낼 수 있다. 실력의 여지를 남긴다.
- UI에 `⚡ 구제` 배지로 두 글자를 나란히 띄워, 규칙을 설명 없이도 알게 한다.

### 4.4 완충 장치 2종

| 기능 | 횟수 | 비용 | 효과 |
|---|---|---|---|
| **패스** | 판당 1회 | HP 10 | 같은 글자 그대로 상대에게 턴을 넘긴다 |
| **힌트** | 판당 2회 | HP 5 | 가능한 단어의 앞 2글자를 보여준다 |

## 5. 게임 모드

### 5.1 v1 — 싱글: AI 기사와의 대전 ✅ 이번 범위

> 게임 관리자 검수 관점 *"혼자서도 할 수 있는가 — 상대가 없으면 못 노는 게임은 접속했다 그냥 나갑니다"* 에 대한 답이다.

**싱글을 v1의 본체로 삼는 이유:**
1. **끝말잇기는 싱글이 성립하는 드문 종목이다.** 상대의 수가 사전 안에서 나오므로
   AI가 사람과 거의 구별되지 않는다. 마피아·라이어처럼 심리전이 빠지는 손실이 없다.
2. **판정이 이 게임의 성패**인데, 판정 로직은 싱글에서 전부 검증된다.
   **판정이 흔들리는 상태로 멀티를 붙이면 두 배로 되돌려야 한다.**
3. 멀티는 접속·대기 인원이 필요해 "지금 당장 해보는" 경험을 못 준다.

### 5.2 v1.1 — 온라인 1:1 대전 (다음 단계)

- **턴제**라 공용 브로커 지연에 안전하다(BRIEF 지침 준수).
- `games/ox-survival/index.html:351` 의 브로커 3중화(`emqx`/`hivemq`/`mosquitto`) +
  재연결 패턴을 그대로 계승한다. **방장 브라우저 권위** 모델.
- 사전이 양쪽에 동일하게 내장되므로 판정 결과가 갈리지 않는다 — 방장이 최종 판정한다.
- ⚠ 알아둘 것: ox-survival은 mqtt.js를 **CDN에서 불러온다**(`index.html:352`).
  따라서 **멀티는 인터넷이 있어야 하고, 싱글은 MQTT에 전혀 의존하지 않게 분리한다.**
  오프라인 `file://`에서도 싱글은 완전히 동작해야 한다.

> **미결 — 관리자 판단 요청:** 1:1 온라인 대전은 `games/duel/`(1대1 대전 담당) 과 성격이 겹칠 수 있다.
> 중복 투자인지, 종목이 달라 무방한지 게임 관리자 판단을 받고 v1.1에 착수하겠다.

## 6. 전투 시스템

단순 체인 잇기가 아니라 **HP 대결**로 만든다. "배틀"이라는 이름값과 기사 컨셉을 동시에 만족시키고,
*긴 단어·어려운 단어를 빨리 낼수록 유리*하다는 목표를 플레이어에게 준다.

```
양쪽 HP 100. 먼저 0이 되는 쪽이 패배.

유효한 단어 = 공격
  피해 = (단어 길이 × 2)
       + (희귀 글자 j q x z v 포함 시 글자당 +4)
       + (남은 시간 비율 × 10)

시간 초과 / 패스 / 힌트 = 자신에게 피해
  시간 초과 15 · 패스 10 · 힌트 5
```

- 5글자 단어를 여유 있게 내면 약 17 피해 → **한 판 12~16턴, 2~3분.** 짧게 여러 판 하는 리듬.
- **제한시간**: 15초에서 시작해 5턴마다 2초씩 줄고 **최소 7초**. 후반에 긴장이 오른다.
- 화면에 피해량이 튀어오르는 연출로 "왜 이만큼 깎였는지" 즉시 보이게 한다.

### 6.1 수치는 `TUNE` 한 곳에 모은다

위 수치는 **계산상 추정치이고 실제 플레이 후 조정한다.** 조정이 쉽도록
`game.js` 상단에 상수 객체 하나로 모으고, 코드 곳곳에 숫자를 흩지 않는다.
(무한의 계단이 게이지 수치를 `TUNE`으로 모아둔 선례를 따른다 — 게임 관리자 제안)

```js
var TUNE = {
  HP: 100,
  DMG_PER_LEN: 2,          // 단어 길이당 피해
  DMG_RARE: 4,             // 희귀 글자(j q x z v) 1개당 가산
  DMG_TIME_MAX: 10,        // 남은 시간 비율에 곱할 최대 보너스
  SELF_TIMEOUT: 15,        // 시간 초과 자해
  SELF_PASS: 10, SELF_HINT: 5,
  TURN_SEC: 15, TURN_MIN: 7, TURN_STEP: 2, TURN_EVERY: 5
};
```

## 7. AI 설계

| 난이도 | 단어 풀 | 응답 시간 | 실패 확률 | 구제 글자 활용 |
|---|---|---|---|---|
| **견습** | `core.js` 기초어 + 4~6자 | 5~8초 | 12% | 안 씀 |
| **기사** | 3~9자 | 3~5초 | 5% | 가끔 |
| **검성** | 전체 | 2~3초 | 0% | **적극적으로 막다른 글자로 끝냄** |

- **응답 시간을 일부러 지연**시킨다. 즉답하면 사람과 겨루는 느낌이 사라진다.
- 검성은 `x`/`z`로 끝나는 단어를 우선 선택해 플레이어를 몰아붙인다 — 난이도 조절 손잡이가
  "빠르기"만이 아니라 **전략**이 되게 한다.
- AI도 재사용 금지·차단 목록을 동일하게 지킨다.

## 12. 스스로 아는 미비점

- **현대어 누락이 가장 큰 잔여 위험이다.** ENABLE은 1997년경 리스트라 `email` `internet`
  `online` `app` `wifi` 가 없다. `extra.js`로 메우지만 **손으로 고르는 목록이라 빠뜨린 게 반드시 남는다.**
  §2.4의 "거부된 단어 목록 + 복사 버튼"이 이걸 사후에 잡는 유일한 장치다.
- `dict.js` 168,452개는 **전수 품질 검사가 불가능**하다. 자동 검사(중복·길이·문자집합·정렬)는
  통과했지만(중복 0, 비알파벳 0), **부적절어는 차단 목록으로만 방어**한다 — 빠짐이 있을 수 있다.
- ~~사전 파일이 모바일 첫 로딩에 부담~~ → **해소.** 532KB / 로딩 32ms 실측(§2.3). 분할 불필요.
- **`file://` 동작은 아직 실측 전이다.** 로컬 서버(http)로만 확인했다. 화면을 붙인 뒤
  실제 `file://` 더블클릭으로 재확인한다.
- 한글 뜻은 `core.js` 수록어(1,000개)에만 붙는다. 나머지 16만여 단어는 뜻 없이 지나간다.
- §4.2의 구제 글자 선정식(`배율 ≥ 2.0` + `시작 < 1,000`)은 **ENABLE 실측값에 맞춰 역으로 도출한
  기준**이다. `extra.js`를 더하면 글자별 수치가 조금 움직이므로, 최종 굽기 시점에 재확인한다.
- 초안에서 **`y`를 구제 대상에서 뺐던 판단은 틀렸다**(§4.1). 사전의 절대 개수만 보고
  학습자 기준 가용 개수를 보지 않은 실수였고, 실측으로 뒤집었다.

## 15. 게임 방식

끄투 온라인의 핵심을 그대로 가져온다 — **한 방에 여러 명이 들어가 순서대로 단어를 잇고,
못 내면 체력이 깎여 탈락한다. 최후 1인이 승리한다.**

| 항목 | 값 | 이유 |
|---|---|---|
| 인원 | **2~8명** | 8명이면 자기 차례가 8턴에 한 번. 더 늘리면 기다리기만 한다 |
| 턴 | 참가 순서대로 순환 | 끄투와 동일 |
| 체력 | 각자 100 | 싱글과 같은 감각 |
| 실패 | 시간 초과 시 **-15**, 0이 되면 **탈락(관전 전환)** | 한 번 못 냈다고 바로 나가면 재미가 없다 |
| 승리 | **최후 1인** | 무한의 계단 멀티와 같은 배틀로얄 구조 |
| 점수 | 성공한 단어의 피해 공식값 누적 | 탈락해도 순위가 남는다 |
| 단어 중복 | **방 전체가 공유** | 앞사람이 쓴 단어는 아무도 못 쓴다 |
| 구제 글자 | 싱글과 동일 (`x`·`y`) | 규칙을 두 벌 만들지 않는다 |

**싱글의 공격 개념은 멀티에 넣지 않는다.** 여럿이 서로를 때리면 누가 누구를 때렸는지
따라가기 어렵고, "내가 못 내서 깎였다"가 훨씬 직관적이다. 좋은 단어의 보상은 **점수**로 준다.

### 15.1 시간 제한
싱글과 같이 15초에서 시작해 한 바퀴(전원 1턴)마다 1초씩 줄이고 **최소 7초**.
인원이 많을수록 한 바퀴가 길어지므로 턴 수가 아니라 **바퀴 수**를 기준으로 삼는다.

## 16. 통신 구조

**방장 브라우저 권위** — BRIEF의 지침이자 OX 서바이벌·캐치마인드와 같은 모델이다.

```
방장  : 판정 · 타이머 · 턴 진행 · 탈락 처리 전부 담당. 상태를 retain으로 브로드캐스트
참가자: 자기 차례에 단어를 보내기만 한다. 화면은 받은 상태를 그리는 것뿐
```

판정을 방장이 독점하므로 **참가자마다 결과가 갈릴 수 없다.** 사전이 모두에게 동일하게
내장돼 있어 방장의 판정과 참가자의 예상이 어긋나지도 않는다.

### 16.1 토픽
`net.js`가 방 코드에서 토픽 ID를 유도한다(방 코드는 토픽에 드러나지 않는다).

| 토픽 | 방향 | retain | 내용 |
|---|---|---|---|
| `wb/<id>/st` | 방장 → 전원 | ✅ | 방 전체 상태(참가자·체력·턴·체인·요구 글자) |
| `wb/<id>/ev` | 참가자 → 방장 | ✗ | 입장 / 단어 제출 / 퇴장 |

retain을 쓰므로 **늦게 들어온 사람도 즉시 현재 상태를 받는다.** 브로커가 바뀌어도
방장이 다시 발행하면 따라붙는다.

### 16.2 네트워크 지연 보정 (중요)
참가자의 제출은 항상 늦게 도착한다. 방장이 자기 시계로만 자르면 **멀리 있는 사람이
억울하게 죽는다.** 그래서 방장은 마감 후 **`GRACE_MS`(700ms)까지 도착한 제출을 받아준다.**

BRIEF가 *"실시간 동기화가 들어가면 공용 브로커 지연 때문에 억울한 판정이 생긴다"*고
경고한 지점이 정확히 여기다. 턴제라 그 위험이 이 한 곳으로 좁혀졌고, 유예로 덮는다.

### 16.3 방장이 나가면
**방을 닫는다.** 참가자에게 알리고 첫 화면으로 보낸다. 두 경로로 잡는다.

| 경우 | 방법 | 걸리는 시간 |
|---|---|---|
| 나가기 버튼 | 방장이 `ph:'closed'`를 발행 | 즉시 |
| **탭을 그냥 닫음 · 브라우저 종료 · 네트워크 끊김** | **참가자 쪽 감시 장치** | 약 22초 |

**탭을 닫는 경우에 알림을 보낼 수 없다** — 암호화가 비동기라 페이지가 사라지는 순간에
발행을 끝내지 못한다. 그래서 참가자가 **방장의 침묵을 직접 감시**한다.
방장은 조용할 때도 5초마다 상태를 다시 알리고(하트비트), 참가자는 13초간 소식이 없으면
다른 브로커로 옮겨 찾아보고, 26초까지 없으면 끊긴 것으로 판단한다.

떠나는 쪽의 통지에 기대지 않고 **남는 쪽이 판단**하므로, 탭 닫힘·브라우저 종료·
네트워크 단절을 한 방법으로 전부 잡는다.

방장 승계(host migration)는 누가 새 방장인지 합의하는 과정이 필요해 v1.1 범위를 넘는다.
**알려진 한계로 남긴다.**

### 16.4 멀티는 https에서만 된다
`net.js`가 쓰는 `crypto.subtle`은 보안 컨텍스트를 요구한다. **`file://` 더블클릭에서는
멀티가 막히지만 싱글(AI 대전)은 그대로 동작한다** — 싱글이 네트워크에 전혀 의존하지 않게
짠 이유다. 첫 화면에서 멀티를 고를 때 이 사실을 안내한다.

1. **나가기 알림이 나가지 못했다.** `pub`이 비동기(AES-GCM)인데 곧바로 `end(true)`로
   강제 종료해 프레임이 유실됐다. → 발행 완료를 기다린 뒤 **정상 종료**로 바꿨다.
   증상은 "참가자가 나가도 게임이 끝나지 않음"이었다.
2. **방장이 나갔다는 알림을 스스로 덮어썼다.** 알림을 보낸 뒤에도 진행 타이머가 살아 있어
   `hostTimeout → pubState`가 정상 상태를 다시 발행했다. → **알림 전에 타이머부터 끊는다.**
3. 방을 나간 뒤 늦게 도착한 상태에 `M`이 `null`이라 걸려 넘어질 수 있었다. → 방어 코드 추가.

### 19.4 남은 미비점

- **방장 승계 없음.** 방장이 나가면 방이 닫힌다 (§16.3).
- **참가자가 탭을 닫으면 유령이 남는다.** 자기 차례마다 시간 초과로 체력이 깎여 결국
  탈락하므로 게임은 진행되지만, 그동안 다른 사람이 기다려야 한다.
- **8명 동시 접속은 검증하지 못했다.** 탭 3개까지만 실제로 붙여봤다.
- **공용 브로커 지연을 실제 원거리 환경에서 재보지 못했다.** 같은 기기의 탭 사이라
  지연이 거의 0이었다. `GRACE_MS`(700ms)가 충분한지는 실사용으로 확인해야 한다.
- **멀티는 https에서만 된다** (§16.4). `file://`에서는 싱글만 동작한다.

## 20. v1.1.1 — 배경 탭 방어 (게임 관리자 지적 반영)

### 20.1 무엇이 문제였나

게임 관리자가 탭 3개로 진행하던 중 **방장은 멀쩡히 게임을 돌리고 있는데
참가자 두 명이 모두 "방장과 연결이 끊겼습니다"로 튕겨 나갔다.**
한 방에서 양쪽 인식이 갈라졌다.

원인은 `WATCH_DEAD=26000` 한 줄이었다. **브라우저는 숨은 탭의 타이머와 소켓을 조인다.**
배경 탭은 가만히 있어도 26초 침묵을 넘긴다 — 폰에서 메신저를 한 번 확인하고 오면
방에서 쫓겨난다는 뜻이었다.

**검증 중 확인한 사실:** 이 테스트에 쓴 배경 탭은 실제로 `document.hidden === true`였다.
관리자가 겪은 환경이 정확히 이것이다.

**`net.js`(전송 계층)는 캐치마인드에서 가져왔으면서 그 위의 배경 탭 대응은 가져오지 않은 것이
누락의 실체다.** 계층 하나만 복사하고 그 계층을 쓰는 쪽의 대응을 빠뜨렸다.

### 20.2 고친 방법 — 임계값이 아니라 "관측 가능성"

임계값을 늘리는 것으로는 못 고친다. 숨어 있는 동안의 침묵은 **애초에 판단 근거가 아니다.**

| 처리 | 내용 |
|---|---|
| **숨은 동안 판단 중지** | `document.hidden`이면 감시 루프가 그냥 돌아간다. 관측할 수 없는 것으로 판단하지 않는다 |
| **복귀 시 기준 재설정** | 돌아온 순간 `seenAt`을 다시 잡되, **기준점은 `WATCH_PROMOTE`(탐색 시작)이지 `WATCH_DEAD`(사망 확정)가 아니다** — §20.6 |
| **임계값 상향** | 침묵 판정 26초 → **50초** (캐치마인드 `DROP_MS`와 동일) |
| **브로커 반복 탐색** | 아래 §20.3 |
| **재입장 가능** | 참가자 ID를 `sessionStorage`에 고정. 튕겨도 같은 사람으로 되돌아간다. 방 코드를 입력칸에 남겨 [참가] 한 번이면 복귀 |

### 20.3 검증 중 새로 찾은 결함 — 브로커 탐색을 한 번만 했다

연결 장애를 재현하다 **방장과 참가자가 서로 다른 브로커로 흩어지는 상황**을 실제로 만났다.

```
방장   : wss://broker.emqx.io      (재연결 시도 중)
참가자 : wss://broker.hivemq.com   (연결됨, 그러나 방장이 없음)
```

한 번 끊기면 양쪽이 **각자 브로커 목록을 돌기 때문에** 다른 곳에 앉을 수 있다.
그런데 참가자의 탐색은 `M.promoted` 플래그로 **한 번만** 시도하고 끝났다.
→ `WATCH_HOP`(6초)마다 **반복해서 목록을 훑도록** 고쳤다 (캐치마인드의 `HOP_MS`/`BROKER_HOPS`와 같은 방식).

### 20.4 검증

| 항목 | 결과 |
|---|---|
| 숨은 탭에서 방장 침묵 72초 | ✅ **쫓아내지 않음** (수정 전에는 26초에 튕김) |
| 탭 복귀 후 진짜 끊김 감지 | ✅ **7.0~7.5초** (`RETURN_GRACE` 6초 + 판정 주기) |
| 방 코드 유지 | ✅ 입력칸에 남아 [참가] 한 번으로 복귀 |
| 진행 중인 방에 재입장 | ✅ **2초**, 같은 사람으로 인식됨 |
| 정상 대전 회귀 | ✅ 18초에 15단어, 구제 글자(`early`→`ladder`) 정상 |
| 콘솔 에러 | ✅ 0 |

### 20.5 남은 한계

- **참가자가 숨은 탭에 있는 동안 방장이 죽으면 알 수 없다.** 돌아왔을 때 알게 된다.
  관측할 수 없는 것을 판단하지 않기로 한 결과이고, 이게 옳은 쪽이다.
- **방장 탭이 숨으면 진행이 거칠어진다.** 브라우저가 인터벌을 최소 1초로 조이므로
  턴 전환이 최대 1초쯤 늦어질 수 있다. 판정 자체는 `Date.now()` 기준이라 어긋나지 않는다.
- **양쪽이 다른 브로커로 흩어진 뒤 50초 안에 못 만나면 방이 끊긴다.** 탐색을 반복하도록
  고쳤지만 공용 브로커를 쓰는 한 완전히 없앨 수는 없다.

### 20.6 재검수에서 잡힌 것 — 복귀 유예를 잘못된 문턱에 걸었다

게임 관리자 지적: 복귀 시 기준점을 `WATCH_DEAD`에 걸어 놓았다.

```js
M.seenAt = Date.now() - Math.max(0, WATCH_DEAD - RETURN_GRACE);   // ✗ 50초 기준
M.seenAt = Date.now() - Math.max(0, WATCH_PROMOTE - RETURN_GRACE); // ✓ 20초 기준
```

**모양은 캐치마인드와 같은데 뜻이 정반대였다.** 원본은 *"돌아왔으니 잠시 뒤부터 찾아보자"*인데
이쪽은 *"돌아왔으니 잠시 뒤에 죽었다고 하자"*가 됐다. 실제 동작:

| 시각 | gap | 수정 전 | 수정 후 |
|---|---|---|---|
| +8초 | 22초 | (이미 끊김) | 탐색 1회차 |
| +16초 | 30초 | — | 탐색 2회차 |
| +24초 | 38초 | — | 탐색 3회차 |
| +32초 | 46초 | — | 탐색 4회차 |
| +6초 / +37초 | | **끊김 확정** | 끊김 확정 |

**"복귀 후 7초 만에 감지"라고 보고했던 수치가 바로 이 결함이었다.** 빠른 감지로 읽었지만
같은 수치가 **오탐까지 7초 만에 낸다**는 뜻이었다. 폰은 탭을 벗어나면 WebSocket이 멈추고
돌아와 재연결하는 데만 몇 초가 걸리므로, 살아 있는 사람이 그대로 튕긴다 —
고치려던 증상이 자리만 옮겨 남아 있었다.

### 20.7 그 검증에서 또 나온 것 — retain이 감시를 무력화했다

기준점을 고친 뒤 실측했더니 **참가자가 죽은 방장을 영영 감지하지 못했다.**

브로커는 마지막 상태를 **retain** 해 둔다. 참가자가 브로커를 옮길 때마다
**죽은 방장의 낡은 상태가 다시 배달되고**, 그걸 생존 신호로 받아들여 타이머가 초기화됐다.
탐색을 반복하게 만든 §20.3 수정이 오히려 이 경로를 열었다.

→ 상태에 **발행 일련번호 `q`** 를 붙였다. 참가자는 *"메시지를 받았다"* 가 아니라
**"번호가 늘었다"** 를 생존의 근거로 삼는다. 같은 번호가 다시 오면 브로커에 남아 있던
낡은 상태일 뿐이므로 무시한다.

**받은 사실과 살아 있다는 사실은 다르다** — retain을 쓰는 구조에서는 반드시 구분해야 한다.
