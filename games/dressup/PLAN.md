# 옷입히기 게임 — 기획안 (v1, 검토용)

작성: 게임 관리자(claude-1b) / 2026-08-27
상태: **기획 단계. 코드 미착수.** 컨셉 확정 후 전담 직원 배정 예정.

---

## 0. 전제 — 가장 먼저 정해야 할 것

이 게임의 성패는 컨셉보다 **"옷 그래픽을 어떻게 조달하는가"**에 달려 있습니다.

공통 사양상 외부 라이브러리·서버·이미지 CDN을 쓸 수 없으므로, 선택지는 사실상 하나입니다:
**모든 옷/캐릭터를 인라인 SVG로 직접 그린다.**

이건 제약이 아니라 오히려 유리합니다. SVG는 색상 변경(`fill` 교체)이 코드 한 줄이라
**"같은 옷 × 색상 8종" = 아이템 8개**로 뻥튀기가 가능합니다. 아이템 볼륨 문제를 그리기 노동 없이
해결할 수 있어서, 아래 세 안 모두 이 방식을 전제로 설계했습니다.

대신 리스크가 있습니다: **옷이 캐릭터 몸에 안 맞으면 게임이 통째로 망가집니다.**
그래서 어떤 안을 고르든 첫 작업은 "캐릭터 1명 + 옷 3벌이 정확히 겹쳐 보이는지" 검증부터입니다.

## 1. 컨셉 3안

### A안 — 클래식 드레스업 (자유 코디)

가장 정통적인 형태. 캐릭터가 가운데 서 있고, 좌우에 카테고리 탭(헤어/상의/하의/신발/액세서리)이 있어
아이템을 눌러 갈아입힙니다. 목표도 점수도 없고, 마음에 드는 코디가 나오면 저장하거나 이미지로 뽑습니다.

- **재미의 축**: 조합의 자유도. 아이템이 많을수록 재미있어짐
- **장점**: 구조가 단순해 버그가 적고, 아이템만 계속 추가하면 성장하는 구조
- **단점**: **게임이 아니라 도구에 가깝습니다.** 목표가 없어 3분이면 할 게 없어짐.
  허브의 아케이드 톤과도 가장 안 어울리는 안
- **규모**: 소 (전담 직원 1명 기준 가장 빠름)

### B안 — 랜덤 코디 챌린지 ★ 관리자 추천

A안의 코디 화면을 그대로 쓰되, **제시어와 제한시간을 얹습니다.**

라운드가 시작되면 화면에 미션이 뜹니다 — 예: `#여름 #청량 #데이트`.
플레이어는 60초 안에 그 무드에 맞게 코디를 완성하고, 제출하면 채점됩니다.
점수는 각 아이템에 미리 붙여둔 태그가 미션 태그와 얼마나 겹치는지로 계산합니다
(예: 민소매 = `여름/청량`, 패딩 = `겨울/포근`). 색 조합 보너스/감점도 넣을 수 있습니다.
5라운드 누적 점수 → 랭크(S/A/B/C) → localStorage 최고 기록 갱신.

- **재미의 축**: "이 무드에 뭘 입혀야 하지?"라는 판단 + 시간 압박
- **장점**: A안의 모든 자산을 그대로 쓰면서 **게임이 됨**. 반복 플레이 동기(점수 갱신)가 생기고,
  제한시간·랭크 연출이 허브의 아케이드 톤과 정확히 맞습니다. 미션 조합만 바꿔도 콘텐츠가 늘어남
- **단점**: 채점 로직이 납득되게 나와야 함. "왜 이게 낮은 점수지?" 소리가 나오면 재미가 깨지므로,
  **채점 결과에 이유를 보여주는 UI가 필수**입니다 (예: "여름 태그 3/4 일치, 색 조합 +10")
- **규모**: 중 (A안 + 태그·채점·타이머·결과화면)

### C안 — 스타일 서바이벌 (AI 심사 배틀)

미션을 받고 코디한 뒤, **컴퓨터가 만든 코디와 1:1로 붙어** 이기면 다음 라운드로 진출하는 토너먼트.
지면 탈락. OX 서바이벌과 같은 "살아남기" 결이라 허브 안에서 톤이 통일됩니다.

- **장점**: 긴장감이 가장 높고, 허브 내 다른 게임과 세계관이 이어짐
- **단점**: **B안의 채점 로직이 완성돼야 그 위에 얹을 수 있습니다.** 컴퓨터 코디 생성 AI,
  대전 연출, 토너먼트 진행까지 붙으면 작업량이 B안의 2배 가까이 됩니다.
  채점이 부실한 상태로 대전을 붙이면 "쟤가 왜 이겨?"가 되어 B안보다 더 크게 망합니다
- **규모**: 대

### 비교표

| | A안 자유 코디 | **B안 랜덤 챌린지** | C안 스타일 서바이벌 |
|---|---|---|---|
| 게임성 | 낮음 (도구에 가까움) | **중** | 높음 |
| 허브 톤 적합도 | 낮음 | **높음** | 매우 높음 |
| 반복 플레이 동기 | 거의 없음 | **점수 갱신** | 토너먼트 돌파 |
| 작업 규모 | 소 | **중** | 대 |
| 핵심 리스크 | 금방 질림 | 채점 납득성 | 채점 + 대전 밸런스 |
| 확장 여지 | 아이템 추가 | → C안으로 확장 가능 | — |

### 관리자 의견

**B안을 권합니다.** 이유는 세 가지입니다.

1. A안은 완성해도 "게임 허브에 올릴 게임"이 아니라 꾸미기 도구입니다. 카드 눌러 들어온 사람이
   1분 만에 나갑니다.
2. C안은 결국 B안의 채점 로직 위에 얹는 구조입니다. **B안 없이 C안을 바로 만들 수 없습니다.**
3. 따라서 B안으로 먼저 완성해 게임을 하나 확보하고, 반응이 좋으면 **그 자산 그대로 C안으로
   확장**하는 게 가장 손실이 적습니다. B안은 A안을 포함하므로(자유 코디 모드를 옵션으로 남길 수 있음),
   B안 하나로 세 안의 가치를 대부분 회수할 수 있습니다.

## 2. 공통 사양 (안과 무관하게 고정)

| 항목 | 내용 |
|---|---|
| 기술 | 바닐라 HTML/CSS/JS. 빌드 도구·프레임워크·외부 라이브러리 **없음** |

| 필수 UI | 좌상단 "← 허브로 돌아가기" 링크 (현 placeholder와 동일 위치) |
| 등록 | 완성 후 `data/games.js`의 `dressup` 항목 `status: "wip"` → `"ready"` 변경 |

## 3. 사용자 결정이 필요한 선택지

컨셉 확정과 함께 아래도 정해주시면 직원에게 한 번에 내려보낼 수 있습니다.
**전부 정하기 부담스러우시면 1번만 정해주셔도 착수 가능합니다** — 나머지는 관리자 추천안으로 진행하겠습니다.

| # | 항목 | 선택지 | 관리자 추천 |
|---|---|---|---|
| 1 | **컨셉** | A / B / C | **B** |
| 2 | 그림 스타일 | ① 마네킹형(얼굴 없는 심플 실루엣) ② 치비 캐릭터(2~3등신, 얼굴 있음) ③ 네온 아웃라인 | **①** — SVG로 옷 맞추기가 가장 쉽고 실패 위험이 낮음. ②는 귀엽지만 옷 정합성 난이도가 확 올라감 |
| 3 | 캐릭터 | ① 1명 고정 ② 체형/피부톤 2~3종 선택 | **①로 출시 후 ②를 확장으로** — 체형이 늘면 옷 SVG를 체형 수만큼 그려야 함 |
| 4 | 저장 기능 | ① 없음 ② localStorage에 최고점수만 ③ 코디 슬롯 저장까지 | **②** — B안은 점수 갱신이 재밌음의 핵심. ③은 UI가 커짐 |
| 5 | 결과 내보내기 | ① 없음 ② PNG 다운로드 ③ 결과 카드 화면만 | **③** — 참고: 허브를 Artifact로 배포한 환경에서는 페이지가 시작하는 다운로드가 차단될 수 있어 ②는 안 될 위험이 있음. GitHub Pages 직접 접속에서는 정상 동작 |
| 6 | 초기 아이템 수 | ① 최소 (카테고리당 3~4) ② 넉넉히 (카테고리당 6~8) | **①로 완성 → 이후 추가** — 아이템은 나중에 늘리기 가장 쉬운 부분. 먼저 게임을 돌아가게 만드는 게 우선 |
| 7 | 사운드 | ① 없음 ② 효과음 (Web Audio 합성) | **②** — 파일 없이 코드로 생성 가능. 타이머 압박감에 효과가 큼 |

## 4. B안 확정 시 예상 작업 분할 (참고)

전담 직원 1명(`model: "opus"`)에게 다음 순서로 지시할 계획입니다.
**1단계에서 정합성이 안 나오면 즉시 보고받고 2번(그림 스타일)을 재검토합니다.**

1. **캐릭터 + 옷 SVG 정합성 검증** — 캐릭터 1명, 옷 3벌 겹쳐 그리기. 여기가 통과해야 나머지가 의미 있음
2. 코디 화면 — 카테고리 탭, 아이템 목록, 착용/해제, 색상 변형
3. 게임 루프 — 미션 생성, 타이머, 제출
4. 채점 + 결과 화면 — 태그 매칭, **점수 근거 표시**, 랭크, localStorage 최고 기록
5. 모바일 대응 + 허브 등록(`games.js` `status` 변경)

각 단계 완료 시 관리자가 검수 후 다음 단계 지시. 1~5 일괄 지시하지 않습니다.
