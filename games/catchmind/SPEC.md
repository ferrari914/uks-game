## 1. 아키텍처
OX 서바이벌(`games/ox-survival/index.html`)과 **동일한 통신 모델**을 쓴다.
- 공용 MQTT 브로커(WebSocket) 3중 폴백 → `wss://broker.emqx.io:8084/mqtt`, `wss://broker.hivemq.com:8884/mqtt`, `wss://test.mosquitto.org:8081/mqtt`
- mqtt.js는 CDN 2중 폴백(unpkg → jsdelivr)
- **방장 브라우저가 심판(권위)**: 라운드 진행·타이머·정답 판정·점수 계산은 전부 방장 기기에서 하고 결과만 뿌린다
- 방장이 창을 닫으면 방이 닫힌다 (OX와 동일, README에 명시)
- 서버 없음. GitHub Pages 정적 배포. **HTTPS 필수** (`file://`·`http://`에서는 wss 차단 → 멀티 불가)

### 파일 구성 (ES 모듈 금지 — `file://`에서 깨진다. 전부 classic script)
```
games/catchmind/
├─ index.html   마크업 + CSS + 부팅 (허브 다크 테마 계승)

```
로드 순서: `words.js` → `net.js` → `game.js`.

## 2. 모드
### 개인전 (기본)
- 2~8명. 각자 경쟁.
- 출제자는 **입장 순서대로 로테이션**.

### 팀전
- 레드 vs 블루. 2:2 / 3:3 / 4:4 (최대 8명).
- **시작 조건**: 4명 이상 + 양 팀 인원 동일. 조건 미달이면 시작 버튼 비활성 + 사유 표시.
- 출제자의 **같은 팀원만 정답 입력 가능**. 상대팀 입력은 정답 판정하지 않고 일반 채팅으로 처리(정답 단어가 들어 있으면 마스킹).
- 출제자는 레드 → 블루 → 레드… 번갈아 나온다.
- 승패는 팀 점수 합계로 가린다. 동점이면 무승부.

## 3. 라운드 정의 (중요)
**1 라운드 = 참가자 전원이 한 번씩 출제하는 한 바퀴.** (skribbl.io 방식)
- 예: 5명 × 3라운드 = 총 15턴.
- 설정 화면의 라운드 버튼(3/5/7/10) 옆에 **예상 소요 시간**을 같이 보여준다
  (`인원 × 라운드 × (제한시간 + 8초)` 를 분 단위로 반올림). 10라운드가 얼마나 긴지 보이게 하는 목적.
- 화면 상단에는 `라운드 2/5 · 3번째 차례 / 5` 처럼 둘 다 표시한다.
- 팀전에서도 동일(한 바퀴에 전원이 한 번씩, 팀 번갈아).

## 4. 방장 설정 (대기실, 방장만 조작)
| 설정 | 값 | 기본 |
|---|---|---|
| 모드 | 개인전 / 팀전 | 개인전 |
| 라운드 | 3 / 5 / 7 / 10 | 3 |
| 라운드 제한시간 | 60 / 90 / 120초 | 90 |
| 난이도 | 쉬움 / 보통 / 어려움 / 전체 | 전체 |
| 카테고리 | 다중 선택 (전체 선택이 기본) | 전체 |
| 힌트 | 켜기 / 끄기 | 켜기 |

- 설정은 `localStorage`에 저장해 다음 판에 복원한다.
- **자동 시작은 절대 없다.** 인원이 몇 명이든 방장이 "게임 시작"을 눌러야 시작한다.
- 시작 불가 사유(인원 부족, 팀 불균형)는 버튼 아래에 한 줄로 띄운다.

## 5. 라운드 진행
```
pick(제시어 선택 10초) → draw(제한시간) → reveal(정답 공개 5초) → 다음 턴 … → final
```

### (1) pick
- 출제자에게만 조건(난이도·카테고리)에 맞는 **제시어 3개 후보**를 준다 → 1개 선택.
- 10초 안에 안 고르면 첫 번째 자동 선택.
- 나머지 참가자 화면: "○○님이 제시어를 고르는 중…"

### (2) draw
- 출제자: 캔버스 + 도구바 활성, **채팅 입력 잠금**(제시어 노출 방지).
- 나머지: 캔버스는 보기 전용, 채팅으로 정답 도전.
- **정답을 맞힌 사람은 그 라운드 동안 채팅 입력이 잠기고** 목록에 "정답!" 배지가 붙는다 (정답 누설 차단).
- 종료 조건: (출제자 제외) 전원 정답 **또는** 시간 초과.
- 힌트(켜짐일 때): 처음부터 글자 수를 `_ _ _`로 표시. 남은 시간 60% 지점에 무작위 한 글자, 30% 지점에 한 글자 더 공개(최대 `길이-1`자까지).

### (3) reveal
- 정답 공개 + 이번 턴 획득 점수 표(누가 몇 점, 출제자 몇 점).
- 아무도 못 맞혔으면 "아무도 못 맞혔습니다" 표시.

### (4) final
- 개인전: 1~3위 시상대 + 전체 순위표.
- 팀전: 팀 점수 비교 + 팀별 개인 기여도.
- "대기실로" 버튼 → 점수 초기화 후 대기실 복귀(방장이 다시 시작 가능).

## 6. 점수
| 대상 | 계산 |
|---|---|
| 정답자 | `40 + round(60 × 남은시간/제한시간)` (40~100점) |
| 정답 순위 보너스 | 1등 +15, 2등 +10, 3등 +5 |
| 출제자 | 맞힌 사람 1명당 **+20점**. 아무도 못 맞히면 0점 |

- 출제자도 득점하므로 "잘 그려서 맞히게 하는 것"이 이득이다(원본 3항의 협력적 인센티브).
- 팀전 팀 점수 = 팀원 개인 점수 합.

## 7. 정답 판정 (방장 기기에서)
- 정규화: 앞뒤/중간 **공백 제거**, 영문 **소문자화**, `.,!?~-` 등 특수문자 제거.
- 제시어 본문 또는 `a`(별칭) 배열 중 하나와 일치하면 정답.
- **근접 판정**: 정규화 후 편집거리 1 이하 & 길이 2자 이상이면 **본인에게만** "아깝다! 거의 맞았어요" 시스템 메시지. (다른 사람에게는 그 채팅이 보이지 않는다 — 정답 힌트 누설 방지)
- 정답인 채팅은 원문을 뿌리지 않고 `○○님 정답! (+85)` 시스템 메시지로 대체한다.
- 라운드 중이 아닐 때(대기실·reveal)의 채팅은 그냥 채팅이다.

## 8. 캔버스
- 논리 좌표 **800×600 고정**, CSS로 반응형 스케일(비율 유지). 좌표는 **0~1 정규화 실수(소수 3자리)**로 전송 → 기기 해상도 무관.
- 입력: Pointer Events(마우스·터치·펜 공통). 그리는 중 페이지 스크롤 방지(`touch-action:none`).
- 도구: 색상 12종 팔레트, 굵기 4단계(2/6/12/24), 지우개, 전체 지우기, 되돌리기(스트로크 단위), 채우기(선택 — 여유 있으면).
- 출제자 안내: "글자·숫자를 쓰지 마세요" 문구를 도구바에 상시 노출(강제 불가, 안내만).

### 드로잉 전송 (공용 브로커라 양 조절이 핵심)
- 별도 토픽 `/d`로 보낸다(상태 메시지 지연 방지).
- **80ms 배치**로 모아서 전송. 배치당 좌표쌍 최대 40개.
- 다운샘플링: 직전 점과의 거리가 논리좌표 2px 미만이면 버린다.
- 메시지: `{t:'s',c,w,e}` 스트로크 시작(색/굵기/지우개) · `{t:'p',p:[x,y,…]}` 좌표 배치 · `{t:'e'}` 끝 · `{t:'clr'}` · `{t:'undo'}`
- 늦게 들어오거나 재접속한 사람: `{t:'sync',uid}` 요청 → **출제자**가 지금까지의 스트로크 스냅샷을 보낸다(200 스트로크 초과 시 오래된 것부터 잘라 보냄).

## 9. 통신 프로토콜
토픽: `ekcm/<방코드>/s` (방장→전원 상태) · `ekcm/<방코드>/c` (참가자→방장) · `ekcm/<방코드>/d` (출제자→전원 드로잉) · `ekcm/<방코드>/p/<uid>` (방장→개인)

- 방 코드 5자리(대문자+숫자, 헷갈리는 `O/0/I/1` 제외). 초대 링크는 `…/index.html#ABC12`. **코드만으로도 입장된다.**
- 참가자→방장: `join` / `chat` / `ping`(3초) / `team` / `pick` / `sync` / `leave`
- 방장→전원: `state`(참가자·점수·페이즈·라운드·남은시간·힌트) / `chat` / `round` / `end`
- **제시어는 절대 전원 토픽에 싣지 않는다.** 출제자 개인 토픽 `p/<uid>`로만 보낸다.

### 방 코드만으로 입장 (v2 — 사용자 확정 2026-08-28)
**초대 링크 없이 방 코드 5자만으로 들어갈 수 있어야 한다.** 그런데 키를 방 코드에서 그냥
유도하면 안 된다 — 방 코드가 MQTT 토픽 이름(`ekcm/<코드>/s`)에 그대로 들어 있어서,
`ekcm/#` 와일드카드로 구독한 제3자가 토픽에서 코드를 읽어 그대로 키를 만들 수 있다.
암호화가 통째로 무의미해진다.

그래서 **방 코드 하나에서 서로 다른 두 값을 유도하고, 토픽에는 코드가 나타나지 않게 한다.**

- **토픽 ID** = `SHA-256(코드 + 솔트1)`의 앞 16 hex자 → 토픽은 `ekcm/<토픽ID>/s` 형태.
- **암호화 키** = `PBKDF2(코드, 솔트2, 250000회, SHA-256)` → AES-GCM 256비트.
- 솔트가 다르므로 토픽 ID에서 키를 역산할 수 없고, 토픽 ID에서 방 코드도 되돌릴 수 없다.
- 결과: 와일드카드 구독자는 `ekcm/a3f9…/s`와 암호문만 본다. **코드를 아는 친구는 그냥 들어온다.**
- **⚠ `crypto.subtle.digest`는 async다.** 토픽 함수(`tS()` 등)는 동기이므로,
  방 생성·입장 시점에 토픽 ID를 한 번만 계산해 `S.tid`에 저장하고 그 뒤로는 동기로 쓴다.
  연결·구독보다 반드시 먼저 계산돼야 한다.
- 초대 링크는 `…/index.html#ABC12` (코드만). 입력창은 링크 전체 / `#코드` / `코드` /
  소문자 / 옛 형식 `코드-키`를 전부 받아들인다(옛 링크를 붙여넣는 사람이 있다).
- AES-GCM은 브라우저 내장 Web Crypto라 라이브러리·CDN이 늘지 않는다. 보안 컨텍스트(HTTPS)
  전용이지만 `wss://` 때문에 어차피 HTTPS가 전제다.
- **⚠ 순서 보장**: `crypto.subtle`은 전부 async라 그냥 호출하면 스트로크 순서가 뒤집힌다.
  발행(`pubQ`)·수신(`recvQ`) 각각에 프라미스 체인 큐를 둬 직렬화한다. 낱개 좌표마다
  암호화하지 말고 80ms 배치 단위로만 호출한다.
- **한계는 그대로 적는다**: 방 코드를 아는 사람은 당연히 다 읽는다. 막는 것은 코드를 모르는
  제3자의 브로커 도청뿐이다. 코드가 5자(약 3,300만 조합)라 캡처한 암호문을 오프라인에서
  무차별 대입하는 것이 이론적으로 가능하다 — PBKDF2 반복이 그 비용을 올릴 뿐이다.
  → README 12-b에 정직하게 명시.
- 방 코드 5자리(헷갈리는 O/0/I/1 제외)는 그대로 둔다. 사람이 불러주기 좋은 길이가 우선이고, 보안은 위 한계대로다.
- 12초 넘게 ping이 없는 참가자는 목록에서 제거(OX와 동일). 그 사람이 출제자면 **진행 중이던 턴을 무효 처리(아무도 득점 없음)하고 즉시 다음 턴**으로 넘어간다. 채팅에 "○○님의 연결이 끊겨 이번 차례를 넘깁니다" 시스템 메시지.
- **방장 이탈 = 방 종료**(OX와 동일). 참가자 화면에 "방장이 나가 방이 닫혔습니다" 안내 + 홈으로 버튼. 방장 화면에서 이탈 시도 시 게임 중이면 "방이 닫힙니다" 확인창.
- 남은 인원이 2명 미만이 되면 게임을 중단하고 대기실로 돌아간다.
- 게임 도중 들어온 사람은 **관전**하다가 다음 라운드부터 참가(점수 0으로 합류).

## 10. 화면
0. **공통** — 모든 화면 좌상단에 `← 허브로` 링크(`../../index.html`). 게임 중에는 "정말 나가겠습니까?" 확인을 받는다.
   - **접근성**: 이 링크는 `aria-label="허브로 돌아가기"`를 달고 터치 타깃 **44×44px 이상**이어야 한다. 이름을 `title` 속성에만 의존하지 않는다(마피아에서 실제로 지적된 항목이다 — 처음부터 맞춘다).
1. **홈** — 닉네임(최대 8자) + 아바타 이모지 선택 / `새 방 만들기` / `방 코드로 입장`. 링크에 `#코드`가 있으면 "초대받은 방 ABC12" 카드가 바로 뜬다.
2. **대기실** — 참가자 목록(방장 왕관), 팀전이면 레드/블루 선택, 방장 설정 패널, 초대 링크 복사, `게임 시작`.
3. **게임** — 상단: 라운드/턴·타이머·제시어 힌트 / 좌: 플레이어 목록+점수(+팀) / 중앙: 캔버스(+출제자 도구바) / 우(모바일은 하단): 채팅.
4. **오버레이** — pick(제시어 3택), reveal(정답+점수), final(결과).

## 11. 디자인·접근성

## 12-b. 치팅에 대한 정직한 한계 (README에 그대로 적을 것)
서버가 없으므로 **결심한 사람의 치팅은 막을 수 없다.** 과장하지 말고 아래를 그대로 적는다.
1. **`words.js`는 모든 참가자에게 전송된다.** 제시어 풀 전체가 공개돼 있으므로, 힌트(글자 수·공개 글자)로 후보를 좁히면 개발자도구 없이도 찍을 수 있다. 제시어를 해시로 보내는 식의 대책은 **의미가 없다** — 공격자가 공개된 풀 전체를 같은 방식으로 해시해 맞춰보면 되기 때문이다.
2. **방장은 심판이라 정답을 알 수밖에 없다.** 정답 판정을 방장 기기에서 하는 구조상 방장이 출제자가 아닌 라운드에도 방장 브라우저에는 제시어가 존재한다. 서버 없이 이걸 없앨 방법은 없다.
3. 그래서 v1이 실제로 막는 것은 **우발적·저비용 노출**뿐이다: 제시어를 전원 토픽에 싣지 않고, 토픽 이름에 방 코드를 노출하지 않고, 페이로드를 암호화하고, 정답 채팅 원문을 뿌리지 않는다.
3-b. **방 코드가 5자(약 3,300만 조합)라, 캡처한 암호문을 오프라인에서 무차별 대입하는 것이 이론적으로 가능하다.** PBKDF2 250,000회가 후보 하나당 비용을 올릴 뿐, 작정한 상대를 막는 장치는 아니다.
4. 결론: **친구끼리 즐기는 용도.** 상금이 걸린 자리에는 쓰지 말라고 적는다.
